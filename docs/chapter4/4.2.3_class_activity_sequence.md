# 4.2.3 Class Diagram

![Figure 4.x: PARP class diagram](diagrams/png/class.png)

*Figure 4.x: PARP class diagram*

	Figure 4.x shows the static structure of PARP as domain classes, their attributes and operations, and the two services that hold the system's core logic. The User hierarchy mirrors the use case diagram: User is abstract and holds identity, credentials, role and account status together with the operations every account shares, namely registration, login, logout, profile update and search. Student adds the content and communication operations, Lecturer specialises Student with the Super Like operations and its staff identifier, and Administrator carries the moderation operations. Modelling Lecturer as a subclass of Student, rather than as a sibling, expresses in the type structure the same rule the server enforces at run time: a lecturer can do everything a student can, plus verification.

	Post is the central content class and is composed of one or more Slide objects, drawn as composition because a slide has no existence outside its note and is deleted with it. Comment is likewise composed into Post and has a reflexive association that represents one level of replies. Post is associated with Hashtag in a many-to-many relationship, and with Like, Verification, Bookmark, Report and Interaction as association classes that record who acted on which note and when. The messaging classes are separated from content: MessageRequest holds a first message from a non-friend and creates a Conversation when accepted, Conversation is composed of Message objects, and both MessageRequest and Message carry an optional association to Post, which is the class-level expression of post-anchored messaging (FR7).

	RankingService and SearchService are drawn as service classes because they own behaviour that spans many entities. RankingService exposes one operation per component of the scoring formula in Section 2.3.4, namely engagement, recency, validation and relevance, together with buildInterestVector and the composite score operation. Separating the components into individual operations allows each to be unit tested against fixed inputs, which is the verification approach committed to in Section 2.3.4.10. Every weight and constant is read from RankingConfig, a single configuration object whose initial values are those of Section 2.3.4.7, so that the re-evaluation of the weights required by NFR5 after user acceptance testing changes one file and no scoring code.

# 4.2.4 Activity Diagrams

	Five activity diagrams describe the workflows that carry the project objectives: publishing a note, browsing the ranked feed, lecturer verification, searching, and post-anchored messaging. Each diagram separates the actor and the system into swimlanes, so that the boundary between user decisions and system processing is explicit.

![Figure 4.x: Activity diagram for publishing a slide note](diagrams/png/act_publish_note.png)

*Figure 4.x: Activity diagram for publishing a slide note*

	Figure 4.x describes how a student or lecturer creates and publishes a slide note (UC05 to UC07). The author edits slides in a loop until the content is complete and then assigns a module and hashtags. The first decision separates saving a draft from publishing; a draft is stored without completeness checks so that unfinished work is never lost. When the author publishes, the system presents the three visibility options at equal prominence, which implements FR10's requirement that no option is visually favoured, since the survey found no option above 40.6 percent preference. Completeness is validated only at this point, and a failure returns the author to the editor with the missing items listed. On success the system normalises the hashtags, stores the note, and builds the full-text search document that later serves FR12. The final decision displays the lecturer badge when the author is an approved lecturer, which is the authorship component of lecturer validation.

![Figure 4.x: Activity diagram for browsing the ranked feed](diagrams/png/act_ranked_feed.png)

*Figure 4.x: Activity diagram for browsing the ranked feed*

	Figure 4.x shows how the ranked feed is produced and consumed (UC09), and is the workflow that delivers Objective 1. After retrieving the notes the viewer is permitted to see, the system builds the viewer's interest vector and then calculates the four score components. These are drawn as parallel activities between a fork and a join because they are independent of one another; engagement depends only on like and comment counts, recency only on age, validation only on authorship and Super Likes, and relevance only on hashtags and the interest vector. The weighted sum then orders the page. The lower half of the diagram shows the browsing loop, in which every note that remains on screen is recorded as a view interaction. This feedback loop is what makes the ranking adaptive: each view, like and comment shifts the interest vector used for the next request.

![Figure 4.x: Activity diagram for lecturer verification](diagrams/png/act_lecturer_verification.png)

*Figure 4.x: Activity diagram for lecturer verification*

	Figure 4.x covers both stages of lecturer verification: the approval of a lecturer account (UC22) and the Super Like of a note (UC19). The first stage was introduced during design to protect the trust signal; a user who registers as a lecturer receives student-level rights until an administrator confirms the staff identity. The second stage applies three guards in sequence before a verification is stored. The server checks the role and status regardless of what the interface displays, rejects a lecturer's attempt to verify their own note because authorship already contributes V = 0.5, and treats a repeated Super Like as idempotent. Only after all three checks does the note receive the verified frame and the maximum validation value, which addresses FR1 and FR2 and feeds FR3 through the ranking formula.

![Figure 4.x: Activity diagram for searching content](diagrams/png/act_search.png)

*Figure 4.x: Activity diagram for searching content*

	Figure 4.x describes the search workflow (UC14) that serves Objective 2. The system first classifies the query so that each type uses its most selective access path: a hashtag query matches the normalised hashtag index, a module code matches the unique module code, and any other text uses the full-text index across titles, slide content and hashtags as well as module, programme and user names. This classification covers the three search keys of FR4 and the free-text requirement of FR12. Visibility restrictions are applied before the optional lecturer and date filters, which implement the reworked FR15. The latency timer that starts before the query and is logged after it is the measurement point for NFR1, so that the three-second target is evidenced from recorded timings rather than observation.

![Figure 4.x: Activity diagram for post-anchored messaging](diagrams/png/act_post_anchored_message.png)

*Figure 4.x: Activity diagram for post-anchored messaging*

	Figure 4.x shows how a user messages the author of a note (UC15 and UC16), which delivers Objective 4. The message always carries the note it was sent from, so the conversation opens with its academic context attached. The first decision applies FR6: messages between friends (two users who follow each other) are delivered immediately, while a message to a non-friend is held as a request. Duplicate requests are prevented, and the recipient's decision determines the outcome. Accepting creates the conversation and moves the held message into it, but does not make the two users friends; declining closes the request without notifying the sender. This design reflects the survey finding that 75 percent of respondents wanted approval before receiving messages from non-friends, while keeping the note-anchored first message that 78.1 percent rated useful.

# 4.2.5 Sequence Diagrams

	The sequence diagrams show the same five workflows at the level of the implemented architecture: the React client, the Express API with its Passport JWT middleware, the service classes, the Socket.io server for real-time messaging, and the PostgreSQL database. Messages are numbered so that each step can be referenced from the test cases in Section 4.5.

![Figure 4.x: Sequence diagram for publishing a slide note](diagrams/png/seq_publish_note.png)

*Figure 4.x: Sequence diagram for publishing a slide note*

	Figure 4.x shows the publish request passing through two layers of checks before any data is written. The authentication middleware rejects missing or invalid tokens and inactive accounts, and the controller rejects incomplete content with a 400 response listing each error, matching the exception flows of UC07. The service then writes the post, its slides, any new hashtags, the post-hashtag links and the search document inside a single transaction. A transaction is used because a note that is partially stored, for example with slides but without hashtags, would be visible in the feed with a relevance score of zero and would be absent from hashtag search; atomicity guarantees that a published note is either complete or absent.

![Figure 4.x: Sequence diagram for generating the ranked feed](diagrams/png/seq_ranked_feed.png)

*Figure 4.x: Sequence diagram for generating the ranked feed*

	Figure 4.x shows that RankingService reads all weights and constants from the configuration module at the start of every request, then retrieves candidate posts with their aggregated counts and the viewer's recent interactions in two queries. The scoring loop runs in the application rather than in SQL so that each component is a separately testable function and the arithmetic is identical to the formula in Section 2.3.4. Each component is constant-time per post, which satisfies the responsiveness argument used to justify the deterministic approach in Section 2.3.4.9. The final exchange shows the view interaction being recorded, closing the loop that updates the interest vector for later requests.

![Figure 4.x: Sequence diagram for lecturer verification](diagrams/png/seq_lecturer_verification.png)

*Figure 4.x: Sequence diagram for lecturer verification*

	Figure 4.x shows that verification is authorised on the server through a role-checking middleware placed after authentication, so a student who calls the endpoint directly receives a 403 response even though the interface never shows the button. The controller then distinguishes three outcomes with separate status codes: a missing or unpublished post, an attempt to verify one's own note, and a successful verification. The insert uses the unique constraint on the post and lecturer pair, so a repeated request cannot create a second verification. The note at the end records that no ranking data is updated at this point; the next feed request reads the new verification and scores the post with V = 1.0, which keeps the ranking free of stored scores that could become stale.

![Figure 4.x: Sequence diagram for searching content](diagrams/png/seq_search.png)

*Figure 4.x: Sequence diagram for searching content*

	Figure 4.x shows search from the user's keystrokes to the rendered tabs. The client waits 300 milliseconds after the last keystroke before sending a request, which avoids a query per character without delaying a completed query noticeably. SearchService classifies the query and issues one of three parameterised queries; the full-text branch uses websearch_to_tsquery against the GIN-indexed search document and ranks results with ts_rank. All branches apply visibility and optional filters and limit the result size, and a second query returns matching people. The elapsed time is returned in the response and logged, giving the measured evidence required to evaluate FR5 and NFR1 in Chapter 6.

![Figure 4.x: Sequence diagram for post-anchored messaging](diagrams/png/seq_post_anchored_message.png)

*Figure 4.x: Sequence diagram for post-anchored messaging*

	Figure 4.x shows messaging over Socket.io, where the connection is authenticated with the same JSON Web Token during the handshake, so every event already carries a verified sender. MessagingService checks friendship first, which is a mutual follow: a row in FOLLOW_T in each direction. For friends, the message is stored with its post reference and pushed to a room named after the recipient, so delivery reaches every device on which the recipient is connected. For non-friends, the message is stored as a pending request, and a partial unique index in the database rejects a second pending request between the same pair, so the duplicate check cannot be bypassed by concurrent requests. Acceptance is processed in one transaction that updates the request, creates the conversation and moves the held message, so a request is never marked accepted without the conversation that should accompany it. Acceptance does not create follow rows, because friendship is decided only by the users' own follows.
