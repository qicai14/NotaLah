# 4.3 Database Design

## 4.3.1 Entity Relationship Diagram

![Figure 4.x: PARP entity relationship diagram](diagrams/png/erd.png)

*Figure 4.x: PARP entity relationship diagram (crow's foot notation)*

	Figure 4.x presents the relational data model of PARP as twenty-four entities in crow's foot notation. The model is organised around two central entities. USER_T holds every account, with a single role attribute distinguishing students, lecturers and administrators rather than three separate tables, because the three roles share all identity attributes and a lecturer differs from a student only in permissions. POST_T holds each slide note and references its author and its module; the slides themselves are stored in SLIDE_T as an ordered one-to-many child, since a note contains a variable number of slides that must keep their sequence. A post may exist without a module only while it is a draft, and a check constraint enforces that a published post always has a module, a visibility value and a publication time, which keeps the feed and search queries free of incomplete rows.

	The entities around POST_T map directly to the four components of the ranking formula in Section 2.3.4. LIKE_T and COMMENT_T provide the like and comment counts for the engagement component E. The publication time on POST_T provides the age for the recency component R. VERIFICATION_T records each lecturer Super Like and, together with the author's role, determines the lecturer validation component V. HASHTAG_T, linked to posts through the associative entity POST_HASHTAG_T, and INTERACTION_T together provide the relevance component M: INTERACTION_T is an append-only log of the views, likes and comments each user performs, from which the viewer's decayed interest weight for each hashtag is calculated. Storing raw interactions instead of a pre-computed interest vector keeps the 14-day decay exact and allows the weights to be re-tuned after user acceptance testing (NFR5) without migrating stored data.

	The remaining entities serve engagement, moderation and messaging. COMMENT_T references itself through cmt_parent_id to support one level of replies (FR16), and COMMENT_LIKE_T supplies the like counts that order student comments beneath pinned lecturer comments. BOOKMARK_T implements the saved-notes list (FR14), and REPORT_T together with ACCOUNT_ACTION_T record the moderation workflow, including which administrator resolved each report or changed each account status. FOLLOW_T records who follows whom, one row per direction; when two users follow each other they are friends, who may see each other's contacts-only notes (FR10) and message each other directly. Messaging is separated into MESSAGE_REQUEST_T, which holds a first message from a non-friend until the recipient approves it (FR6), and CONVERSATION_T, CONV_MEMBER_T and MESSAGE_T, which hold direct and group conversations (FR13); approving a request opens that conversation without making the two users friends. Both MESSAGE_REQUEST_T and MESSAGE_T carry an optional reference to POST_T, which is how a message is anchored to a specific note (FR7, Objective 4). For legibility, Figure 4.x draws one relationship line per pair of entities, except FOLLOW_T, which is drawn twice because it references USER_T as both follower and followee; the second foreign keys to USER_T in MESSAGE_REQUEST_T, REPORT_T, CONVERSATION_T and ACCOUNT_ACTION_T are listed in Table [[next]].

	Two entities were added after the first design to meet the scale and reliability targets, and a third replaced an earlier one. FOLLOW_T replaced the original CONTACT_T, which stored a symmetric pair created by an accepted message request. A directed follow with a composite primary key and a check that a user cannot follow themselves is a single relationship from which friendship is derived at query time as a pair of follows in opposite directions, so there is no second table that could drift out of step; the migration that introduced it copied each existing contact into both directions. FEED_SNAPSHOT_T stores, for one viewer and one request time, the ranked list of post identifiers and their scores as arrays. The first page of the For You feed ranks the candidates once and writes this row, and later pages read a slice of it, so that a viewer paging through the feed sees a stable order and the ranking work is not repeated for every page; rows are short-lived and are deleted when they expire. RATE_LIMIT_T is an operational table with no foreign key to any other entity: it holds one counter per rate-limit key (a user identifier or an address) and time window, so that the request limits are enforced consistently across several server instances. It is therefore drawn in Figure 4.x as a standalone entity.

	Three entities support shared notes (R30), which were added after the first design. COLLABORATOR_T grants a user view or edit access to one note, with a composite primary key so that a user holds one role per note; the owner is never a row, because ownership is already recorded in pst_usr_id. SHARE_LINK_T stores the view and edit links an owner hands out. Only the SHA-256 hash of each random token is kept, so a copy of the database cannot be used to open shared notes, and a partial unique index allows at most one active link per note and role, which makes regenerating a link revoke the old one. COLLAB_REQUEST_T records a reader's request to collaborate until the owner approves or declines it, with a partial unique index that permits one pending request per note and user. POST_T gained three columns for the same feature: pst_content_edited_at records the last change to the title or slides of a published note, and a lecturer Super Like older than it no longer counts towards V until the lecturer confirms it again, while pst_lock_usr_id and pst_lock_expires_at hold a short soft lock so that only one collaborator edits at a time.

## 4.3.2 Database Schema

	Table [[next]] lists every table, field, data type, size and constraint of the schema. Table names follow the uppercase singular form with a _T suffix, and field names are lowercase with a three-letter table prefix, so that a field's origin is visible in any query. Because PostgreSQL folds unquoted identifiers to lowercase, table names are written in double quotes in every SQL statement so that the live database matches this schema exactly. Six PostgreSQL-specific types are used where a generic type would be weaker: identity columns generate primary keys without separate sequences, TIMESTAMPTZ stores times with their offset so that recency decay is correct regardless of server time zone, TEXT holds slide content of unpredictable length, TSVECTOR stores the pre-processed search document for full-text search (FR12), array types (INTEGER[] and DOUBLE PRECISION[]) hold the ranked list in FEED_SNAPSHOT_T as one row, and BIGINT is used for the two tables expected to grow fastest, INTERACTION_T and MESSAGE_T. The password hash uses CHAR(60) because bcrypt output is always exactly sixty characters.

	The schema is created by the versioned migration file `server/db/migrations/20261013000001_initial_schema.sql`, so that every later change is recorded as a new migration rather than an edit to the live database. Indexes are defined for the access paths that determine performance: published posts ordered by publication time for the feed, the GIN index on pst_search_doc and the hashtag index on POST_HASHTAG_T for the sub-three-second search target (FR5, NFR1), and the user and time index on INTERACTION_T for building interest vectors. Migrations added after the initial schema create further indexes, each for one access path:

- `comment_like_comment_idx` on COMMENT_LIKE_T (clk_cmt_id): counts the likes of each comment when comments are listed.
- `interaction_user_post_time_idx` on INTERACTION_T (int_usr_id, int_pst_id, int_created_at DESC): finds a viewer's latest interaction with a note for the view-logging window and the interest vector.
- `report_post_idx` on REPORT_T (rpt_pst_id): groups reports by note in the moderation queue.
- `message_request_recipient_pending_idx` on MESSAGE_REQUEST_T (mrq_recipient_id), partial on pending requests: lists a recipient's open requests without scanning resolved ones.
- `follow_followee_idx` on FOLLOW_T (fol_followee_id): lists a user's followers and checks the reverse direction of a follow.
- `feed_snapshot_created_idx` on FEED_SNAPSHOT_T (fsn_created_at): deletes expired snapshots.
- `comment_parent_idx` on COMMENT_T (cmt_parent_id), partial on replies: checks whether a deleted top-level comment still has live replies.
- `collaborator_user_idx` on COLLABORATOR_T (clb_usr_id): lists the notes shared with a user.
- `share_link_active_idx` on SHARE_LINK_T (shl_pst_id, shl_role), unique and partial on active links: keeps one active link per note and role.
- `collab_request_pending_idx` on COLLAB_REQUEST_T (crq_pst_id, crq_usr_id), unique and partial on pending requests: one open request per reader and note.
