# R20 pre-UAT audit: bundle, N+1 and caching, security (22 Oct 2026)

Scope: `main` at `ea331eb` (PR #57). Read-only: no source edits, no dev-DB access, no installs. Lighthouse waits for the
live site. Load assumed: FYP-scale UAT (a few hundred users, a few dozen at once in a session) on one Render free
instance (0.1 CPU, 512 MB, Singapore) with Neon free (Singapore, pooled URL); the demo runs locally.

## How it was checked

- **Bundle:** `vp run -r build` run in place. `shared` and `server` built; `client` **failed** (see E1). Client chunk
  sizes below come from CI run 39721119996 (main, 22 Oct 04:15 UTC, same commit), which built green.
- **N+1 and caching:** read every route and repository behind the feed, note detail, search, profiles, messaging,
  notifications and annotations, plus `app.ts`, middleware and the 18 migrations.
- **Security:** read every router for auth, role, ownership, visibility, blocks and restricted/suspended handling;
  zod and rate-limit coverage; uploads; sanitiser and HTML sinks; CSRF, cookies, CORS; Socket.io; share tokens;
  admin routes; logging and Sentry scrubbing; env guards; the Pages proxy. Dependency audit from the same CI run.
- **Measured:** one bcryptjs cost-12 compare takes **314 ms** on a full desktop core (local, 3-run average).

## Findings

### Blocker (live UAT only; the local demo is unaffected)

**B1. bcrypt cost 12 in pure JS can stall the server whenever people sign in** (`server/src/features/auth/passport.ts:16`,
used at `:87` and `server/src/features/auth/routes.ts:66`)
- Impact: one login or registration costs about 0.31 s of a full core, which is about **3 s** on Render's 0.1 CPU. A
  UAT session where 20 testers sign in within a minute queues about 60 s of CPU, and every other request (feed,
  messages, sockets) waits behind it. Unknown emails cost the same, because of the dummy-hash compare. The auth limiter
  allows 60 attempts a minute per IP, which is about 3 times the instance's whole CPU budget, so one script, or one
  campus lab, can freeze the API for everyone while staying inside the limit.
- Fix (needs the user's agreement; record it as a D-entry): lower `BCRYPT_COST` to 10 (about 80 ms on a full core,
  0.8 s on the instance; still at OWASP's minimum for bcrypt). Existing cost-12 hashes keep working because the cost is
  stored in each hash. Optionally re-hash at cost 10 on the next successful login. Also consider lowering
  `RATE_LIMITS.authAttempts` from 60 to about 20. Add one test that the cost constant is 10 so it cannot drift back.

### Should-fix

**S1. Health checks keep Neon awake around the clock** (`server/src/lib/health.ts:11`, `render.yaml:13`,
`Dockerfile` HEALTHCHECK, README step for UptimeRobot every 5 minutes)
- Impact: every `/api/health` runs `SELECT 1`. Render probes the health path continuously while the instance is up,
  the container has its own 30 s HEALTHCHECK, and UptimeRobot every 5 minutes keeps Render from sleeping. Neon's compute
  therefore never reaches its 5-minute scale-to-zero and runs 24/7: about 744 h at 0.25 CU (about 186 CU-hours) a
  month. If that exceeds the Neon free plan's monthly compute allowance, Neon suspends the database until the next
  month. It stops rather than bills, but it means an outage during UAT. Verify the current allowance in Neon's docs.
  The route is also the one path `requireProxy` lets through (`lib/proxySecret.ts:21`) and has no rate limit, so
  anyone can make the database work through the public onrender.com URL.
- Fix: make `/api/health` a liveness answer that does not touch the database (status and version only). Move the
  database probe to `/api/health/db` (or `?db=1`) for the deploy workflow and manual checks. Keep `D34`'s pool timeout,
  which already absorbs Neon's wake-up on the first real request. One test: `/api/health` answers 200 with the pool
  stopped.

**S2. Signed-in reads have no rate limit, and the most expensive read writes to the database**
(`server/src/app.ts:59`, `server/src/features/feed/service.ts:96-100`, `server/src/features/search/routes.ts:40`)
- Impact: the write limiter covers non-GET methods and the guest limiter covers signed-out reads only. A signed-in
  user, or a stuck client loop, can call `GET /api/feed` (page 1) without limit, and each call scores up to 500
  candidates and writes a 500-entry snapshot (`saveSnapshot`). `GET /api/search` does the same scoring over up to 500
  matches. On 0.1 CPU a single account can starve everyone else. `GET /api/programmes` and `GET /api/terms` have no
  auth and no limiter at all.
- Fix: one per-user (else per-IP) read limiter on `/api` GETs, for example 300 a minute through `createLimiter` with
  `userOrIpKey`, mounted next to the write limiter. Exclude asset files, which `fileLimiter` already counts, and
  `/api/health`. One test with `RATE_LIMIT_UNDER_TEST`.

**S3. The web app is served with no security headers** (no `client/public/_headers`; helmet in `app.ts:36` only
covers API responses)
- Impact: Cloudflare Pages serves `index.html` and the JS with no `Content-Security-Policy`, no `X-Frame-Options`
  or `frame-ancestors`, and no `Referrer-Policy`. Any site can frame NotaLah (clickjacking on Like, Follow, Delete,
  Block or the admin actions). XSS safety rests on the server sanitiser alone, with no CSP behind it. Hashed bundles
  also get the Pages default `max-age=0, must-revalidate`, so every page load revalidates every chunk.
- Fix: add `client/public/_headers` with two blocks.
  - `/*`: `X-Frame-Options: DENY`; `Referrer-Policy: strict-origin-when-cross-origin`; `X-Content-Type-Options: nosniff`;
    and a `Content-Security-Policy` with `frame-ancestors` none, `default-src` self, `script-src` self plus the
    sha256 hash of the inline theme script in `index.html`, `style-src` self plus unsafe-inline (React style props),
    `img-src` self, data, blob, images.unsplash.com and the Jamendo image host, `media-src` self, blob and the Jamendo
    audio host, `connect-src` self, wss and the Sentry ingest host, `object-src` none, `base-uri` self.
  - `/assets/*`: `Cache-Control: public, max-age=31536000, immutable`.
  Check every page once in the browser console for CSP errors before UAT (the Jamendo and Unsplash hosts are the
  likely misses). One DEP test that the file exists and carries `frame-ancestors`.

**S4. Image decoding can use about 200 MB of the 512 MB instance** (`server/src/features/assets/config.ts:6`,
`server/src/features/assets/image.ts:16-23`; no `sharp.concurrency` or `sharp.cache` call anywhere)
- Impact: `maxInputPixels` is 50 million, so a 5 MB PNG or JPEG can decode to about 150-200 MB, and `.rotate()` on a
  rotated phone photo can force libvips to hold the whole image. The sharp thread pool defaults to the host's visible
  cores, which inside a 0.1-CPU container can be many, each with its own buffers. Two such uploads at once, or one
  beside an ffmpeg job (`VIDEO_WORKER_IN_PROCESS`) and the 50 MB `readFile` in the video route
  (`assets/routes.ts:160`), can push the container past 512 MB. Render then kills the process: every socket drops,
  the guest ranking cache empties and in-flight saves fail.
- Fix: lower `maxInputPixels` to about 24 million (`maxEdge` 2560 means larger images are scaled down anyway), and
  call `sharp.concurrency(1)` and `sharp.cache(false)` once at startup. Verify with one upload of a 7000x7000 PNG with
  EXIF orientation 6 while watching RSS (`process.memoryUsage().rss`) before and after.

**S5. Restricted accounts can still change their display name and bio** (`server/src/features/users/routes.ts:45`)
- Impact: UC21 says a restricted account may read but not create or edit content. `PUT /api/users/me` has no
  `requireActive`, so a user restricted for abuse can rename themself to something abusive. The name then shows on
  every comment, annotation, message and search result. No D-entry covers this case.
- Fix (confirm the policy with the user): add `requireActive` to `PUT /api/users/me`, plus a USR test that a
  restricted user gets 403. If the user wants restricted accounts to keep profile edits, log that as a decision.

**S6. First paint loads a 193 kB (gzip) entry chunk** (CI build: `index-*.js` 628.43 kB, gzip 192.96 kB;
`index-*.css` 107.97 kB, gzip 22.06 kB)
- Impact: before the shell renders, a mid-range phone has to download and parse about 630 kB of JS. That is the
  likely Lighthouse mobile weak spot (TBT and LCP). Every page is already lazy (15 `lazy()` routes in `App.tsx`), so
  this is the shell plus vendor code: React DOM, react-router, the Radix dialog, sheet, tooltip and dropdown (the
  GuestPrompt sheet and dialog are mounted for everyone), lucide icons, tailwind-merge and `socket.io-client`, which
  `MessagingContext` imports eagerly though guests never connect. The CSS carries `@font-face` rules for all 7 deck
  font families (italic included). Font files themselves load only when used.
- Fix: measure first. After `vp install`, build once with source maps and look at what makes up `index-*.js`. Cheap
  wins: load `socket.io-client` with a dynamic import inside the signed-in effect, and lazy-load the GuestPrompt
  sheet and dialog. Re-check after Lighthouse on the live site.

### Nit

**N1. `notify` runs two queries per recipient, and mentions check visibility one user at a time**
(`server/src/features/notifications/service.ts:16-22`, `:38-41`). There are at most 10 mention candidates and most
notifications have one recipient, so this is bounded. If it ever grows, fold `getNotification` into the INSERT's
RETURNING and send one `unreadCount` query for all recipients.

**N2. Feed and search spend one round trip on `getCutoff`** (`feed/repository.ts:18`). It is a separate
`SELECT NOW()` before every feed, Following and search request. In-region it costs about 1-2 ms, so leave it unless
profiling shows otherwise.

**N3. Index gaps on per-user lists** (`notes/repository.ts:497` profile notes, `:223` drafts,
`engagement/repository.ts:271` bookmarks). These use `post_author_idx (pst_usr_id)` or the bookmark primary key and
then sort. That is fine at this scale. A migration with `"POST_T" (pst_usr_id, pst_status, pst_published_at DESC)` and
`"BOOKMARK_T" (bmk_usr_id, bmk_created_at DESC)` makes them index-ordered if UAT profiles grow.

**N4. Reference lists carry no cache header** (`modules/routes.ts:10-22`). Modules, programmes and terms change only
when an admin edits them, but each page that needs them refetches. `Cache-Control: private, max-age=300` saves the
query. The default Express ETag already gives a 304, but only after the query has run.

**N5. Autosave rewrites the whole deck** (`notes/repository.ts:283-336`). Every autosave (2-10 s while typing)
deletes and re-inserts every slide, hashtag and asset link and rebuilds `pst_search_doc`: about 20 round trips and up
to 1.4 MB of JSONB rewritten. Acceptable for UAT. Note it in Chapter 6 as a scaling limit.

**N6. A lazy chunk is named `dev-*.js`** (420 kB, gzip 141 kB). The only dynamic import that is not a page is
`@sentry/browser` (`client/src/lib/errorReporting.ts:8`), so it is most likely that. It is fetched only when
`VITE_SENTRY_DSN` is set. The name suggests a development-condition build. CI builds with `NODE_ENV=test`
(`ci.yml:34`), while the deploy build does not, so check the chunk name and size in a production build before
turning the client DSN on.

**N7. `listPendingLecturers` is unbounded** (`users/repository.ts:103`). It is admin-only and pending applications
are few. Add `LIMIT 100` if the list ever pages.

## Verified fine

- **SQL:** every query is parameterised. Interpolated fragments are module constants or code-chosen identifiers
  (`SIDES`, `noteCols(CARD_SLIDES)` with `Math.trunc`), never request data. ffprobe and ffmpeg run through
  `execFile` with an argument array.
- **Auth:** the JWT is in an httpOnly, SameSite=Lax cookie, Secure in production (env guard). HS256 is pinned and
  the user is reloaded on every request, so suspended or deleted accounts are refused at once. The sliding session is
  capped at 12 h. Logout clears the cookie and sends `Clear-Site-Data: "cache"`. Login uses a dummy hash for unknown
  emails and a per-IP-and-email failure limiter.
- **CSRF:** every non-GET `/api` request needs `X-Requested-With: notalah`. CORS is locked to `CLIENT_ORIGIN`. Joining
  through an edit link is a POST.
- **Roles and ownership:** the admin router uses `requireAuth` plus `requireRole('admin')` on every route, and so
  does `/admin/usage`. Super Like needs an approved lecturer (not an admin) and refuses one's own or co-authored notes.
  `noteAccess` decides 404, 403 or editable for owner and co-author routes. `requireActive` is on every
  content-creating route except S5.
- **Visibility and blocks:** `VISIBLE`, `READABLE`, `SHAREABLE` and `VISIBLE_OR_ADMIN` are shared fragments. Guests
  (`GUEST_ID` 0) see public notes only. Assets are readable only through a readable note or by their owner. Blocks are
  checked on profiles, comments, annotations, notifications, follows, messaging inserts (inside the INSERT) and typing.
- **Share links:** 256-bit random tokens, stored as SHA-256 hashes, format-checked, revocable. They are replaced in
  request logs and in Sentry events and breadcrumbs on both sides. Link holders get no page notes and no
  friends-only annotations.
- **Socket.io:** the Origin must equal `CLIENT_ORIGIN` and the request must carry the proxy secret (`allowRequest`).
  The handshake authenticates by the same passport rules. Rooms are joined from DB membership. The socket is cut at
  token expiry, and suspension disconnects it. `maxHttpBufferSize` is 1000, and typing is throttled.
- **Uploads:** auth, active account and kill switch are checked before the body is read. Images are content-sniffed,
  re-encoded to WebP and stripped of EXIF. Videos stream to a temp dir, are checked by ffprobe and transcoded by the
  queued worker. The per-user quota uses an advisory lock, and the global and R2 caps are metered. Files are served
  with `nosniff` (helmet), CORP same-site, `private` and `Vary: Cookie`.
- **XSS:** one `dangerouslySetInnerHTML` (`SlideBoard.tsx:82`). It renders HTML sanitised server-side against a
  17-tag allow-list with no links, images or attributes beyond `ol[start]` and `span[style=color:#hex]`. The deck
  schema is strict, and image URLs must be `https://images.unsplash.com/...`. `anchors.ts` uses an inert `<template>`.
- **Validation:** zod covers every body and query that reaches the database. Ids pass `idParam` or `invalidId`.
  Keyset cursors are regex-checked with limit 1-100. JSON bodies are capped at 1 MB (notes 2 MB).
- **Logs:** only id, method and path are logged (no headers, bodies or query strings). `set-cookie` and password
  fields are redacted. `X-Request-Id` is pattern-checked. Production env guards name variables, never values.
- **Proxy:** the Pages Function overwrites (never appends) `X-Forwarded-For`, adds the shared secret, copies only path
  and query onto `API_ORIGIN`, and fails closed. The API refuses requests without the secret.
- **Dependencies:** `pnpm audit --prod --audit-level high` on CI run 39721119996 (main, 22 Oct 04:15 UTC):
  "No known vulnerabilities found". Not re-run locally (no network installs allowed).
