# Search and feed latency at 10x, 29 Oct 2026 (#78, NFR1, ADR 0090)

Target: search and feed p95 under 300 ms at 10 times the UAT-sized load seed. Query plans from `EXPLAIN (ANALYZE,
BUFFERS)`, captured with `auto_explain` on the test database while the API served the real requests.

## Setup

| Item | Value |
|---|---|
| Machine | AMD Ryzen 3 3300X (4 cores, 8 threads), 16 GB RAM, Windows 11 Pro 10.0.26300, Node v24.19.0; probe, API and Postgres 17.11 (Docker) on the same host |
| API | `vp run -r build` output, `node server/dist/server.js` in production mode (README step 3), pool of 10, port 4000 |
| Dataset | `LOAD_USERS=3000 LOAD_NOTES=20000 vp run server#load:seed`, 10 times the default seed: 3,000 users, 20,000 notes (109,998 slides), 238,405 likes, 60,000 comments, 698,405 interactions, 29,900 follows, 1,994 Super Likes, 298 MB. With video: the same plus `LOAD_VIDEO_EVERY=5` (4,000 notes carry one ready video on slide 1) |
| Probe | `vp run server#load:latency`: one signed-in student (load21, follows about ten users), sequential, 5 warm-up then 100 measured requests per endpoint, 210 ms apart (read limiter; the default is now 200 ms, derived from it) |
| Indexes | Those on `main` at 1b15e4b; none added (ADR 0090) |

## Plans

**Keyword and Top search (the gap).** The seed writes every note from a 130-word vocabulary (`data.ts` WORDS) at
about 78 lexemes a note, so one word matches 91% of notes (18,258 of 20,000 for "deadlock"). The planner rightly
picks a sequential scan, and the cost is `ts_rank_cd` on every match before the top 500 can be cut:

```
Limit (rows=500)
  -> Sort  Sort Key: ts_rank_cd(pst_search_doc, '''deadlock'''::tsquery, 1) DESC, pst_published_at DESC, pst_id DESC
           Sort Method: top-N heapsort
     -> Nested Loop (rows=16561)
        -> Seq Scan on "POST_T" p_1 (rows=16561)  Filter: published, visible, pst_search_doc @@ query, ...
        -> Index Only Scan using "USER_T_pkey" on "USER_T" u_1 (loops=16561)
```

Isolated, matching alone takes 31 ms (`count(*)` with the `@@` filter) and matching plus ranking 564 ms. With
`enable_seqscan = off` the planner uses `post_search_idx` (Bitmap Index Scan) and takes 564 ms as well, so no index
removes the cost. Top search runs the same note query plus the people, hashtag and module sections.

**Module search.** `BitmapOr` of `post_search_idx` and `post_module_idx` (667 rows), then ranking those 667.
**Hashtag search.** `post_hashtag_hsh_idx` (359 rows) into `POST_T_pkey`. **Lecturer filter.** The same text match
as keyword search, but the lecturer condition cuts 16,557 rows to 823 before the sort, so the ranking is cheap.
**For You.** `post_feed_idx` for the newest 500 (Incremental Sort, about 4 ms), united with the 1,994 Super Liked
notes in the window (2,494 ids), each checked through `POST_T_pkey`; the per-note counts use `like_post_idx` and
`comment_post_idx`. **Following.** `post_feed_idx` order with the follow check on `FOLLOW_T_pkey`.

Every selective predicate already has an index, so none is added (ADR 0090).

## Gap

Keyword and Top search miss the 300 ms p95 at 10x by about 2.5 times (742 and 735 ms). They stay far inside the NFR1
limit of 3,000 ms. The cause is the volume of matching notes that must be ranked, not a missing index. The seed's small
vocabulary is a worst case: in real notes a term that appears in 91% of all notes is rare. A fix would change the
query (for example, rank a capped set of the newest matches), which changes search results, so it is outside this
ticket.

## Video in the client feed (R29, R40)

One cold load (fresh browser profile, signed in as load21) of the built client (`vp preview` on port 5173, API in
development mode with local storage) in headless Chromium (agent-browser) at a 375 x 812 viewport, on the with-video
seed. A real 4.1 MB, 30 s, 720p MP4 and an 18 KB WebP poster sat at the seeded asset's keys.

| Measure | Value |
|---|---|
| LCP | 964 ms (a text paragraph on the first card) |
| Transferred | 331 KB: 305 KB static (JS, CSS, font), 6 KB API, 19 KB video poster |
| Video bytes | 0: the feed's `<video>` has `preload="none"`; the poster is the only video cost until the viewer plays it |

Video notes add no measurable feed API cost and about 19 KB per preloaded video card, so no video change is needed.
