# Local load evidence, 22 Oct 2026 (R27, NFR1)

Runs of the Node load runner (`server/src/scripts/load/run.ts`) against the built API in production mode on the developer
machine. Raw output per run: `runs/2026-10-22_local_<2k|10k>_<n>vu.md` and `.json`. How to repeat: `README.md`.

## Setup

| Item | Value |
|---|---|
| Machine | AMD Ryzen 3 3300X (4 cores, 8 threads), 16 GB RAM, Windows 11 Pro 10.0.26300, Node v24.22.0; load generator, API and Postgres 17 (Docker, port 5433) on the same host |
| API | `vp run -r build` output, `node server/dist/server.js`, `NODE_ENV=production`, `TRUST_PROXY=2`, `PROXY_SECRET` set (production guards passed; `STORAGE_DRIVER=r2` with dummy values, no upload route used), pool of 10, logs to a file. The server was restarted before every run |
| Datasets | **2k**: 300 users, 2,000 notes (10,998 slides), 22,882 likes, 6,000 comments, 68,882 interactions, 60 days. **10k**: 300 users, 10,000 notes (55,000 slides), 114,212 likes, 30,000 comments, 344,212 interactions. Both seeded with a fixed seed, `ANALYZE` run, re-seeded before each series |
| Scenario | One account, cookie and client address (`X-Forwarded-For`) per VU. One action per iteration by weight (feed p1 20, p2 10, five searches 44, note detail plus view POST 13, comments 5, like 5, comment 3), then think time 0.5 to 1.5 times the mean (1 s unless noted) |
| Limiters | All on, none bypassed (README). A write (view, like, comment) is 22% of iterations, about 12 a minute per VU at 25 VUs, a tenth of the 120/min write limit; no 429 occurred |

**SRCH-TC10 evidence (10,000 notes):** the seeded size the test case names. Sequential and light load (1 and 10 VUs) and 25 VUs
pass with every search under 3 s (worst 2,782 ms at 25 VUs); 50 concurrent users, far beyond UAT scale (at least three
participants), exceed it (p95 4.7 s). The 2,000-note runs are the lighter dataset and are labelled `2k` throughout. The
case's 50 fixed queries are not replayed; the runner's random mix (about 44% searches, five kinds) stands in for them.

Errors were all 404s on `note.detail`, `note.view` and `note.like` (and the paired view): the runner picks a random note id
before it has seen any, and 10% of seeded notes are contacts-only, which a non-follower cannot open. No 5xx, timeout or 429.

## CPU and what the numbers do and do not say

Server-process CPU with the logins separated (a logins-only run of the same VU count, same restart procedure, subtracted):
logins cost about 0.31 s CPU each (bcryptjs, cost 12, on the main thread). Remaining CPU per request, from CPU seconds
over requests: 2k 25 VUs 7.8 ms, 50 VUs 7.5 ms, 100 VUs 7.2 ms; 10k 25 VUs 8.4 ms, 50 VUs 9.7 ms. So about 7 to 10 ms of
API-process CPU per request, excluding Postgres.

- The API process is not what saturates locally: it used about 0.15 to 0.3 of a core while throughput flattened (about
  38 req/s at 2k from 50 VUs, about 16 to 17 req/s at 10k from 25 VUs). Postgres on the same CPU (search over 10,000
  notes, ranking 500 candidates) and the 10-connection pool are the likely limit; I did not profile it.
- Search cost grows with the dataset: at 25 VUs the search median is 160 ms at 2k and 993 ms at 10k (6 times). At 2k, going
  from 50 to 100 VUs raised the search median from 440 to 1,736 ms (3.9 times) with no extra throughput: past the knee the
  closed-loop users only queue.
- Render free gives 0.1 CPU. At 7 to 10 ms of core time per request the API alone would cap near 10 to 14 requests/s even
  if its slice were as fast as this core (it will not be), and a login costs seconds. This is a scaling argument, not a
  measurement; Neon also adds a network round trip per query, and here Postgres has none. Only the live k6 run measures
  Render, Neon, cold start and the Pages hop. The 10k 50-VU failure and the 2k 100-VU tail must not be quoted as the live
  site's behaviour in either direction.
- The generator shares the CPU with the server and Postgres (slightly pessimistic). A shared campus address would meet
  the 60/min login limit; not modelled.
