# Local load evidence, 22 Oct 2026 (R27, NFR1)

Three runs of the Node load runner (`server/src/scripts/load/run.ts`) against the built API in production mode, on the
developer machine. Raw output per run: `runs/2026-10-22_local_{25,50,100}vu.md` and `.json`. How to repeat: `README.md`.

## Setup

| Item | Value |
|---|---|
| Machine | AMD Ryzen 3 3300X (4 cores, 8 threads), 16 GB RAM, Windows 11 Pro 10.0.26300, Node v24.22.0; load generator, API and Postgres on the same host |
| Postgres | 17 in Docker on the same host (port 5433), database `notalah_test_r27_load`, `ANALYZE` run after seeding |
| API | `vp run -r build` output, `node server/dist/server.js`, `NODE_ENV=production`, `TRUST_PROXY=2`, `PROXY_SECRET` set (the production startup guards passed; `STORAGE_DRIVER=r2` with dummy values because no upload route is used), default pool of 10 connections, video worker in process (idle), logs to a file |
| Dataset | 300 users (20 approved lecturers), 2,000 published notes (10,998 slides, 3 to 8 each), 86 hashtags, 30 modules, 22,882 likes, 6,000 comments, 2,924 follows, 68,882 interactions over 60 days, 196 Super Likes; seeded with a fixed seed |
| Scenario | Each VU is one account, logged in once with its own cookie and its own client address (`X-Forwarded-For`). Per iteration one action by weight: feed page 1 (20), feed page 2 (10), search keyword (14), search Top tab (8), hashtag (8), module (7), filtered by lecturer, module and dates (7), note detail then view (13), comments list (5), like (5), comment (3), then a think time of 0.5 to 1.5 s (mean 1 s) |
| Limiters | All enabled, none bypassed (see README): per-VU addresses keep the login (60/min) and write (120/min) limits unreached; no 429 occurred |
| Duration | 90 s per run after the login phase; the runs share one database, so likes and comments accumulate (a few hundred rows) |

## Results

| VUs | Requests | Req/s | Search p50 / p95 / p99 / max (ms) | Feed page 1 p95 (ms) | Errors | NFR1 |
|---|---|---|---|---|---|---|
| 25 | 2,274 | 24.9 | 130 / 369 / 486 / 684 | 313 | 0 | pass |
| 50 | 3,707 | 40.5 | 388 / 884 / 1,117 / 1,371 | 927 | 4 (0.11%) | pass |
| 100 | 4,085 | 44.3 | 1,423 / 2,158 / 2,500 / 2,779 | 2,389 | 8 (0.20%) | pass |

NFR1 test: search p95 under 3,000 ms with no failed search. It held at all three levels, and every single search was also
under 3 s (worst 2,779 ms at 100 VUs). The IR has no separate feed latency requirement; feed figures are reported as
evidence of the same load. Per-endpoint tables are in the run files.

Every error was a 404 on `note.detail` or its follow-up calls, plus the comment and like on the same note: the runner picks a
random note id when it has none yet, and 10% of seeded notes are contacts-only, which a non-follower cannot open. They are
correct answers, not failures (no 5xx, no timeout, no 429 in any run).

Server process CPU (from `Get-Process`): 23.2 s, 39.2 s and 55.5 s for the three runs, resident memory 198, 211 and
216 MB at the end of each run.

## What these numbers do and do not say

- Throughput saturated between 50 and 100 VUs: at 100 VUs the offered load would be about 100 requests/s but only
  44/s were served, and latency rose about 3.5 times at the median. The runner is a closed loop (a VU waits for its answer),
  so past the knee extra users add queueing, not requests. I did not profile which part limits it (one Node thread, the
  10-connection pool and Postgres on the same CPU all contribute).
- Roughly 6 ms of API-process CPU per request (run CPU minus the logins at about 0.33 s of bcrypt each, divided by requests;
  an estimate, and it excludes Postgres CPU). The logins were slow (p50 3 s at 10 at a time) because bcryptjs at cost 12 runs
  on the main thread; they happen once per session, not per request.
- Render free gives the service 0.1 CPU. If one request costs 6 ms on a 3300X core and the free share is much slower than that
  core, the ceiling is of the order of 10 to 15 requests/s with a queue beyond it, and a login costs a few seconds of CPU.
  That is a rough scaling, not a measurement. It suggests NFR1 is comfortable at UAT scale (at least 3 participants, so
  a handful of concurrent users, well below the 25 VU run: 100 to 400 ms searches here), but the 100 VU result must not be
  claimed for the live site. Only the live k6 run (README) measures Render and Neon latency, cold start and the Pages hop.
- Local Postgres has no network hop; Neon adds a round trip per query (several per search or feed request), which the local
  numbers omit. The load generator shared the CPU with the server, which makes the local figures slightly pessimistic.
- A shared address (a campus lab behind one NAT) would hit the 60/min login limit if many users logged in within a minute;
  not modelled here.
