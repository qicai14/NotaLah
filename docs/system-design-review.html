PARP System Design Review

How the system is built today, how it will be deployed (D29), and where the database and the quality attributes stand. It is a basis for your decisions; nothing here has been changed in code.

Short answer

  • The system was designed, but by the autopilot, not with you. The IR fixed the stack and the three tiers; Sprint 0 produced the class, sequence and ER diagrams (Chapter 4) and docs/ARCHITECTURE.md. This page is your chance to accept or change it.
  • Shape: a modular monolith. One Express process with feature modules (auth, notes, feed, ranking, …), each owning its routes and SQL, over one Postgres database. That is the right size for one developer and a few hundred users, and the feature boundaries allow a module to be split out later.
  • Database: sound, normalised, well constrained. Six gaps (four indexes, log retention, pool settings), all cheap to fix in one migration.
  • Weakest quality attributes: observability and deployability. No structured logs, no error tracking, no CI, no container file yet. Security has one known gap (token storage, R1).

Database check

Is the schema already optimised?

Mostly yes. Every table has a primary key, foreign keys and CHECK constraints for each status, the join tables use composite keys, and there are partial unique indexes so a user can hold only one open report or pending message request per target. The feed, author, module, hashtag, full-text (GIN), interaction and message queries are indexed. The gaps below are the ones that will show up as data grows.

Your call

Proposed additions to the backlog

  1. R17 · DB tuning migration (S, Sprint R). The four indexes above, pool settings from env, and a 90-day interaction purge.
  2. R18 · Observability (S, Sprint 5 with deploy). pino request logs with request ids, Sentry free tier on client and server, graceful shutdown.
  3. R11 extended. Compression, credentialed CORS, trust proxy, a dependency audit in CI, and a Lighthouse run against the live site.
  4. Keep the modular monolith. Microservices would add network calls, deployments and failure modes with no benefit at this scale. Chapter 6 can name the split points (ranking, messaging) as future work.
